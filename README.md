# monsterBash_bedControl

Monster Bash 救護所のベッド・椅子の使用状況を、複数人・複数端末でリアルタイムに共有するための Web アプリです。

バックエンドは Firebase（Authentication + Realtime Database）で、アプリ自体はビルド不要の静的ファイルです。GitHub Pages で公開しています。

## 画面構成

| ページ | 内容 | 権限 |
|---|---|---|
| `index.html` | メイン画面。部屋ごとのベッド・椅子の状況、患者の登録・編集・移動・退室、全部屋横断の検索 | 許可ユーザー |
| `discharged.html` | 退室済み一覧、ゴミ箱、CSV書き出し、**日次の締め** | 閲覧は許可ユーザー／締めは管理者のみ |
| `archives.html` | 締めて保存した日ごとの記録（読み取り専用）、CSV書き出し | 許可ユーザー |
| `history.html` | 誰がいつ何を変更したかの履歴 | 許可ユーザー |
| `users.html` | ユーザーの追加・削除、パスワード管理 | 管理者のみ |

各ページはメイン画面のタブ行から移動できます。同じタブ内で開くので、行き来してもタブは増えません。

## 使い方

### ログイン

次の2通りがあり、併用できます。いずれの場合も**許可リストに登録されていないとデータは見えません**。

- **Google アカウント** — 「Googleでログイン」を押す
- **ID とパスワード** — 管理者から配布されたメールアドレスとパスワードを入力

パスワードを忘れた場合は、ログイン画面の「パスワードを忘れた場合」からご自身で再設定できます。

### 患者の受け入れから退室まで

1. 空いているベッドまたは椅子をタップすると編集画面が開く
2. 重症度（軽症・中等症・重症）、氏名、年齢・性別、症状を入力して**保存**
   - 空きから登録したときに患者IDが自動で発番されます
   - 編集画面で選べるのはこの3つだけです。枠が空きに戻るのは**退室**か**移動**のときで、保存で空きにすることはできません（誤って登録した枠は退室して、退室済み一覧からゴミ箱へ入れてください）
3. 状況が変わったら同じ枠をタップして編集
   - **送迎待ち**のチェックで、迎え待ちの状態を示せます
4. 別の枠へ移すときは編集画面の**移動**から移動先を選ぶ
5. 帰られるときは**転帰**（経過観察／帰宅／救急搬送）を選んで**退室**。退室済み一覧に記録が移り、枠が空きに戻る
   - 転帰の初期値は**経過観察**です。帰宅・救急搬送のときは必ず選び直してください

画面下に「保存中です」と出ている間はまだサーバーに届いていません。「保存しました」に変われば反映完了です。保存中に他のページへ移ろうとすると、完了を待ってから移動します。

入室・退室の時刻は `HH:MM` だけを入力しますが、`23:50 入室 → 00:10 退室` のように日付をまたいでも滞在時間は正しく数えます（入力された時刻を、基準になる時刻にいちばん近い日のものとして解釈しています）。

回線が切れると画面上部に警告が出ます。**このときページを閉じたり再読み込みしたりすると、まだ送れていない操作は失われます。** 回線が戻るまでページを開いたままにしてください。

### 患者を探す

部屋タブの下の検索欄に、患者ID・氏名・症状のいずれかを入れると、4部屋すべての埋まっている枠から探します。結果をタップすると、その部屋に切り替わって編集画面が開きます。無線で「1-042の人はどこ？」と聞かれたときに使えます。

隣の **🚐 送迎待ち** ボタンを押すと、送迎待ちにチェックが入っている患者を全部屋分まとめて出します。数字はその件数です。

### 画面が暗くなるのを防ぐ

タブ行の右の **☀️ スリープ防止** を押すと、その端末で画面が自動的に暗くならなくなります。**初期状態はオフ**で、押した状態はその端末に記憶されます。据え置きで表示しっぱなしにする端末だけオンにしてください（電池の消耗が早くなります）。対応していないブラウザではボタン自体が出ません。

### CSVで書き出す

**退室済み一覧**と**保存済みの記録**に「⬇️ CSVで保存」があります。そのとき絞り込んでいる内容がそのまま出ます。Excel で開けるよう UTF-8 の BOM 付きで、時刻は日付込み（`2026-08-22 23:50`）です。撤収後の報告や集計に使ってください。

### 部屋と枠

部屋は **本部・空海横・サーカス・茶堂** の4つです。各部屋にベッド（初期10）・室内椅子（初期4）・室外椅子（初期4）があり、画面上の `＋` `−` で 1〜40 の範囲で増減できます。

枠のIDは部屋ごとに固定で、`B3`（ベッド3番）、`CI2`（室内椅子2番）、`CO1`（室外椅子1番）のように表示されます。

### 患者ID

`2026-1-001` の形式で、**開催年 - 何日目 - 連番3桁** です。画面上は煩雑さを避けて年を省略し `1-001` と表示しますが、保存されるデータには年が入ります。

連番は同時に複数の端末から登録しても重複しません（Firebase のトランザクションで採番しているため）。

### 日次の締め（2日間開催の運用）

1日目が終わったら、退室済み一覧ページの最下部にある**日次の締め**を実行します（管理者のみ）。

実行すると次の4つがまとめて行われます。

1. その日の退室済み一覧とゴミ箱を保存済みの記録へ移す
2. 退室済み一覧とゴミ箱を空にする
3. 患者IDの連番を1に戻す
4. 開催日を1つ繰り上げる（翌日は `2-001` から）

まとめて実行するので、通信が途切れて「消えたのに保存されていない」状態にはなりません。

**入室中の枠が残っていると警告が出ます。** その患者は当日のIDを持ったまま翌日に残り、番号が重複する可能性があるためです。先に退室処理を済ませてから締めてください。

保存した内容は「保存済み」ページで日を選んで閲覧できます。読み取り専用で、復元はできません。

開催年・開催日は締めセクションの「開催年・日を修正」から変更できます。**開催初日の前に、年と日が正しいか確認してください。**

### 変更履歴

登録・編集・退室・移動・台数変更・ゴミ箱操作・ユーザーの増減・日次の締めが、操作した人の名前とともに記録されます。ユーザー・操作種別・キーワードで絞り込めます。

表示名は「許可リストに登録した名前 → Googleアカウントのプロフィール名」の順で決まります。メールアドレスは画面に表示しません。

## 管理者の作業

### ユーザーの追加

`users.html` で、メールアドレス・表示名・パスワード（任意）を入力して追加します。

- **パスワード空欄** — Google アカウントでログインする人向け。許可リストへの登録のみ
- **パスワード入力あり** — ログイン用アカウントも同時に作成。IDとパスワードを本人に渡す
  - この場合は**表示名が必須**です。ID/パスワードのアカウントにはプロフィール名が無く、履歴が「(名前未設定)」になるため

「管理者」にチェックを入れると、ユーザー管理と日次の締めができるようになります。

### パスワードの変更・再設定

- **変更** — 現在のパスワードを知っている場合に、新しいものへ変更する
- **再設定** — 本人宛に再設定メールを送る。パスワードが分からない場合はこちら

なお、パスワードは Firebase の Authentication で暗号化して管理され、**Realtime Database には保存されません**。

### ユーザーの削除

許可リストから消えるとデータには一切アクセスできなくなります。ただし Firebase の認証アカウント自体は残るため、完全に消す場合は Firebase コンソールの **Authentication → Users** から削除してください（クライアント側から他人のアカウントは削除できない仕組みのためです）。

## データ構造（Realtime Database）

すべて `kyuugo/` の下にあります。

```
kyuugo
├─ rooms/{0-3}/{beds|chairsIn|chairsOut}/{枠番号}
│     localId, patientId, patientCode, status, name, sym,
│     waiting, enteredAt, age, gender
├─ globalPatientId          連番カウンタ（締めで0に戻る）
├─ festival                 year（開催年）, day（何日目か）
├─ discharged/{key}         退室記録
│     patientId, patientCode, name, age, gender, sym,
│     room, slotId, kind, triage, outcome,
│     enteredAt, exitedAt, stayMins, recordedAt
├─ discharged_trash/{key}   ゴミ箱（論理削除）
│     退室記録と同じ内容 + trashedAt, reenteredTo
├─ archives/{年}-{日}        締めて保存した日
│     year, day, label, archivedAt, archivedBy,
│     dischargedCount, trashCount, discharged, discharged_trash
├─ auditLog/{key}           変更履歴（追記のみ）
│     at, uid, email, name, action, target, detail
└─ allowedUsers/{メールキー}  許可リスト
      true または { name, admin, authType }
```

- `status` は `empty` / `green`（軽症）/ `yellow`（中等症）/ `red`（重症）
- `outcome`（転帰）は `経過観察` / `帰宅` / `救急搬送`。選択肢は `app-common.js` の `OUTCOMES` が元になっています。転帰を入れる前に記録された古いデータには入っていないので、一覧では「—」と表示されます
- 許可リストのキーは、メールアドレスの `.` を `,` に置き換えたもの（Realtime Database のキーに `.` を使えないため）。例: `yamada.taro@gmail.com` → `yamada,taro@gmail,com`
- `authType` が `password` なら ID/パスワードのアカウント
- 旧データの `used` / `overtime` / `waiting` は現行の4状態に読み替えて表示します

## セットアップ（Firebase）

新しい環境で動かす場合、または設定を確認する場合の手順です。

1. **Authentication → Sign-in method**
   - **Google** を有効化
   - **メール/パスワード** を有効化（ID配布を使う場合）
2. **Authentication → Settings → Authorized domains**
   - `liptonist.github.io` を追加
3. **Realtime Database → データ**
   - 最初の管理者を登録：`kyuugo/allowedUsers/{自分のメールキー}/admin` に `true`（真偽値）
   - 未登録の状態でログインすると、登録すべきキーが画面に表示されます
4. **Realtime Database → ルール**
   - リポジトリの `database.rules.json` の内容を貼り付けて公開

**順序が重要です。** 4を先に実行すると、3を済ませるまで誰もアクセスできなくなります。その状態になっても Firebase コンソールからは操作できるので、3を行えば復旧します。

### セキュリティについて

画面側のログイン制御だけでは防御になりません（画面を迂回してデータベースに直接アクセスできてしまうため）。**`database.rules.json` の適用が実質的な防御線です。**

ルールの要点は次のとおりです。

**誰が入れるか**

- 患者データ・退室記録・履歴・保存済み記録は、**許可リストに載っている人だけ**が読み書きできる
- 開催年・日／保存済み記録の書き込みは**管理者のみ**
- **許可リストは自分の1件しか読めない。**一覧として読めるのは管理者だけ（未設定のときだけ例外的に全体が読める＝初期設定用）。書き換えも管理者のみ
- **ログイン方式を検証する。**Google ログインか、または許可リストに `authType: password` が記録されているアカウントだけを受け付ける
- 許可リストの照合はメールアドレスを**小文字化**してから行う（アプリ側の `emailKey()` と同じ扱い）。登録するキー自体も小文字で `@` を含むことを検証する（大文字のキーは誰とも一致せず、登録しても無駄なため）

**何を消せるか（一般ユーザーの取り消し不能な操作を減らす）**

- **退室記録・ゴミ箱は消せない。**一般ユーザーは追加と、もう一方に控えがある場合の削除（ゴミ箱への移動／一覧への復帰）だけができる。控えのない削除とノード全体の消去は管理者のみ
- **確定した退室記録は書き換えられない。**一般ユーザーができるのは新規追加だけで、既に一覧にある記録の上書き（項目単位の書き換えを含む）は管理者のみ。誤りの訂正は管理者の作業になる
- **部屋の枠をまとめて消せない。**一般ユーザーは枠の中身の更新と枠数の増減はできるが、`kyuugo/rooms` 全体や部屋の `beds` などを丸ごと削除するのは管理者のみ
- 変更履歴は**追記のみ**。既存の記録は改変も項目の追加も削除もできず（管理者も削除できない）、記録者のメールアドレスと UID が認証情報と一致することを検証する

**何を書けるか（内容の検証）**

- 画面を経由しない直接アクセスに備えて、**書き込める形を決めている**。定義にない項目は書けず、型・値の範囲・文字数の上限を検証する
  - `status` は `empty` / `green` / `yellow` / `red` のみ、`waiting` は真偽値のみ
  - 氏名は100文字、症状は1000文字、履歴の補足は1000文字まで
  - `globalPatientId` は 0〜9999 の数値のみ（文字列や負の値を入れて採番を壊せない）
  - 部屋番号は1桁の数字、種別は `beds` / `chairsIn` / `chairsOut` のみ
- 検証は**書き込み時だけ**効きます。既にデータベースにある値は再検証されないため、古い記録も従来どおり読めます

なお HTML に埋め込まれている `apiKey` は公開情報で、隠す必要はありません。Firebase はルールで守る設計です。

#### ルールをローカルで検証する（任意）

ルールは本番のデータベースに直接貼るため、間違えると全員が使えなくなります。手元のエミュレータに当てて確認できるようにしてあります（アプリ本体はこれに依存しません）。

```bash
npm i -g firebase-tools        # Java も必要
firebase emulators:start --only database --project monster-bash-test
# 別のターミナルで
node tools/rules-test.mjs
```

`tools/rules-test.mjs` は次の2つを確認します。

1. **許可と拒否** — 未登録ユーザー・一般スタッフ・管理者それぞれで、通るべき操作が通り、弾くべき操作が弾かれるか
2. **アプリの各手順** — 受け入れ・編集・移動・枠数変更・退室・ゴミ箱・入室に戻す・日次の締め・ユーザー管理を、アプリと同じ形の書き込みでなぞって、ルールが正規の操作を邪魔していないか

`database.rules.json` を触ったら、本番に貼る前にこれを実行してください。

#### ログイン方式の検証はなぜ必要か

「メール/パスワード」を有効にすると、`createUserWithEmailAndPassword` は公開 `apiKey` で**誰でも呼べます**。そのため、許可リストに載っているのに**まだ一度もログインしていない**メールアドレスは、第三者が先にパスワード認証情報を作ってしまうと、そのメールアドレスとしてログインできてしまいます。管理者のアドレスが狙われると被害が大きくなります。

これを防ぐため、ルールとアプリの両方で「Google ログイン、または `authType: password` が記録されているアカウントのみ」を検証しています。`authType: password` は管理者がユーザー管理画面からパスワード付きで作成したときにしか記録されないため、第三者が自作したパスワード認証情報は弾かれます。

あわせて **Authentication → Settings → 「メールアドレスごとに1つのアカウント」を有効**にしておいてください（既にアカウントがあるアドレスの重複作成を防げます）。

> **残る穴が1つあります。**`authType: password` が記録されたまま、Firebase の認証アカウントだけをコンソールから削除すると、そのメールアドレスは「許可リストに載っていて、パスワード認証も許可されていて、アカウントは存在しない」状態になります。第三者が先にパスワード認証情報を作れてしまうため、**認証アカウントを消すときは許可リストの側も必ず消してください**（ユーザー管理画面から削除すれば、許可リストが先に消えるのでこの状態にはなりません）。

> **注意**：ID/パスワードで運用しているのに許可リストに `authType` が記録されていないユーザーは、**ログインできなくなります**。この検証はルールとアプリの両方に入っているため、ルールを貼る前・**コードを反映した時点から**効きます。
>
> 反映前にユーザー管理画面の「ログイン方法」列を確認してください。実際は ID/パスワードなのに `Google` と表示されている人がいれば、「変更」からパスワードを設定し直すと `authType` が補われます（`authType` の記録は 2026-07 の機能追加なので、それ以前に作成したパスワードアカウントが該当します）。

#### 匿名認証を無効にする

匿名認証が有効だと、誰でも `auth != null` の状態を作れてしまいます（許可リストで弾かれるので患者データは読めませんが、有効にしておく理由がありません）。

**Firebase コンソール → Authentication → Sign-in method** を開き、プロバイダ一覧の **「匿名」** を選んで、**「有効にする」のトグルをオフ**にして保存してください。一覧に「匿名」が出ていない、または「無効」と表示されていれば、すでに無効です。このアプリは匿名認証を使っていないため、無効化しても影響はありません。

#### App Check について（任意・未導入）

App Check は「**リクエストが本当に自分のアプリから来ているか**」を検証する仕組みです。ブラウザでは reCAPTCHA（Enterprise / v3）でページを検証し、通ると短命のトークンが発行され、Realtime Database がそのトークンを持たないリクエストを拒否できるようになります。

- **守れるもの**：公開 `apiKey` を使った `curl` や自作スクリプトからの直接アクセス、総当たりでのログイン試行、意図しないコピーサイトからの利用
- **守れないもの**：**正規の利用者による操作**。ログイン済みスタッフが何をできるかは App Check では変わりません。そこは引き続きルールの担当です

つまり App Check はルールの代わりではなく、**ルールの手前にもう1枚の層を足すもの**です。導入手順の概略は次のとおりです。

1. Firebase コンソール → **App Check** → ウェブアプリを登録し、**reCAPTCHA v3** のサイトキーとシークレットを設定
2. 各ページで `firebase-app-check.js` を読み込み、`initializeAppCheck(app, { provider: new ReCaptchaV3Provider('<サイトキー>') })` を `getDatabase()` より前に呼ぶ
3. しばらく**「監視のみ」**で運用し、正規の利用が弾かれていないかメトリクスで確認
4. 問題なければ Realtime Database で App Check を**「適用」**に切り替える

注意点として、`liptonist.github.io` と `/preview/` の両方が対象になること、いきなり「適用」にすると本番中に全員が使えなくなり得ること（必ず「監視のみ」から始める）、reCAPTCHA の実行に外部通信が増えるため電波の悪い会場では失敗しうることを踏まえて判断してください。**イベント本番の直前に入れる変更ではありません。**

### ルールを差し替えるときの順序

ルールはアプリ全体（`main` と `/preview/` の両方）で共有されます。**Firebase プロジェクトは1つで、`/preview/` 専用のデータベースはありません。**そのため、ルールだけを `/preview/` で先に試すことはできません。

新しいルールは「許可リストの全体読み取り」を管理者に限定しているため、**旧コードのままルールを適用すると、一般ユーザーのログインが全員失敗します**（旧 `requireAuth` は許可リスト全体を読もうとするため）。差し替えは次の順序で行ってください。

1. 手元で `node tools/rules-test.mjs` を通しておく（上の「ルールをローカルで検証する」）
2. 新しいコードを `/preview/` に出して動作を確認する（このとき**ルールは旧のまま**。新コードは旧ルールでも動きます）
3. 新しいコードを `main` に反映する
4. そのあとで `database.rules.json` をコンソールに貼り付けて公開する
5. 一般ユーザー・管理者・ID/パスワードユーザーのそれぞれでログインを確認する
6. 受け入れ → 編集 → 退室 → ゴミ箱 → 復帰 を1件通しで試す（内容の検証を追加したため、書き込みが弾かれていないかをここで確認する）

万一ログインできなくなった場合は、コンソールのルールを元の内容に戻せば復旧します（コンソールからのデータ操作はルールの影響を受けません）。

**内容の検証を追加したことによる影響**：検証は書き込み時だけ効くので、既存のデータはそのまま読めます。ただし、古い記録を**書き換える操作**（ゴミ箱への移動・一覧への復帰など）は、その記録が現在の形に合っていないと弾かれます。現行コードが書いた記録はすべて適合していますが、コンソールから手で入れたデータがある場合は形を揃えておいてください。

#### 転帰（outcome）を足したときは順序が逆になります

上の手順は「新コードは旧ルールでも動く」ことが前提です。**書き込むフィールドが増えた変更では前提が崩れます。** ルールは未知の子を拒否するので、`outcome` を書く新コードを旧ルールのまま公開すると、**退室の記録がすべて弾かれます**（退室ボタンを押しても記録が残らない）。

フィールドを増やしたときは次の順序にしてください。

1. 手元で `node tools/rules-test.mjs` を通す
2. **先に** `database.rules.json` をコンソールに貼り付けて公開する（旧コードは新しいフィールドを書かないので、そのまま動き続けます）
3. そのあとで新しいコードを `/preview/` → `main` に出す
4. 受け入れ → 退室 まで1件通し、退室済み一覧に転帰が出ることを確認する

## 開発

ビルドツールもパッケージマネージャもテストもありません。HTML・CSS・バニラJSのみです。

```bash
python3 -m http.server 8000   # http://localhost:8000/index.html
```

`app-common.js` を ES モジュールとして読み込んでいるため、**`file://` で直接開くと動きません。** 上記のようにHTTPで配信してください。

共通処理（Firebase初期化、ログイン、許可リスト判定、保存状態の表示、変更履歴の記録、患者IDの整形）は `app-common.js` にまとめてあります。各ページはここから import します。

### バージョンと修正履歴

メイン画面のタブ行の右端にある **「©」** ボタンから、アプリの名称・バージョン・コピーライト・修正履歴をポップアップで表示します。

表示内容は `app-common.js` の `APP_INFO`（名称・バージョン・コピーライト）と `CHANGELOG`（修正履歴）だけで決まります。修正を出すときは、`APP_INFO.version` を上げて `CHANGELOG` の先頭に項目を追加してください。ポップアップ自体は `showAbout()` を呼ぶだけで開くので、他のページに置くこともできます。

### デプロイ

`.github/workflows/pages.yml` が GitHub Actions で動きます。

- `main` の内容 → サイトのルート
- `claude/feature-branch-html-publish-i9vvl7` の内容 → `/preview/`

どちらかのブランチに push すると自動でデプロイされます。

> **注意**: `claude/feature-branch-html-publish-i9vvl7` はワークフローが直接参照しています。削除するとデプロイが失敗します。

作業の流れは「機能ブランチに push → `/preview/` で確認 → `main` へ反映」です。

`backup/main-20260725` は認証を導入する前の状態を保存したブランチです。削除しないでください。

## 既知の制約

- **同じ枠を同時に編集すると後勝ちになります。** 編集画面は開いた時点の値を保持するため、その間に別の端末が同じ枠を変更していると、保存時に上書きします。別々の枠を触っている限り競合しません
- **保存済みの記録は復元できません。** 誤って締めた場合、Firebase コンソールから手作業で戻す必要があります
- **変更履歴に保持期間の制限はありません。** 長期間使い続けると件数が増え続けます
